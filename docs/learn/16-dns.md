# 16 — DNS: how containers find each other

[Chapter 14](14-veth-bridges-netlink.md) gave containers addresses and [chapter 15](15-nat-nftables.md)
a way out. Addresses aren't names, though, and a container's address
changes from one start to the next. `rustlet network create backend`, then
two containers on it, and the web one can reach the database as `db`,
whatever address `db` got this time. This chapter is about how that works:
the resolver inside a container and the `resolv.conf` the daemon writes
for it, why the default network has no names, the embedded DNS server at
`127.0.0.11` (sockets made inside each container's namespace and served by
the daemon, with port 53 redirected to them), what it answers and what it
forwards, and what a daemon restart does to it.

Code: [`dns.rs`](../../crates/rustlet-net/src/dns.rs) (`Zone`, `View`, `DnsServer`, `answer_locally`;
`serve_udp`, `serve_tcp`, `Shared::forward`, `exchange_udp`, `exchange_tcp`, `fit_udp`),
[`files.rs`](../../crates/rustlet-net/src/files.rs) (`ResolvConf`, `resolv_conf`, `hosts`), the redirect
[`firewall::dns_redirect`](../../crates/rustlet-net/src/firewall.rs); in the daemon,
[`network.rs`](../../crates/rustletd/src/network.rs) (`start_dns`, `dns_names`, `upstreams`, `resume_network`)
and [`lifecycle.rs`](../../crates/rustletd/src/lifecycle.rs) (`run_plan`: the generated files). Tests: the
DNS server's 30 unit tests in `dns.rs` (end to end over loopback against fake upstreams),
`net_dns_port_53_is_redirected_to_the_servers_socket` in [`network.rs`](../../tests/tests/network.rs), and
`dn_user_defined_networks_resolve_their_containers` and `dn_internal_networks_stay_inside` in
[`daemon_network.rs`](../../tests/tests/daemon_network.rs). Design:
[architecture.md §2.5](../architecture.md#25-rustlet-net--host-side-networking) (Files, Embedded DNS).

The transcripts were recorded on 2026-10-02 against the installed service,
kernel 7.0.0-34-generic. The host's resolver is systemd-resolved, whose
upstream is the LAN's router, 192.168.50.1, with the search domain
`lastgateway.lan`. `rustlet` is `sudo target/debug/rustlet`; commands that
need root ran through `sudo systemd-run --pipe --wait`.

## 1. The resolver in a container

A program doesn't speak DNS itself. It calls the C library (`getaddrinfo`),
and the library reads `/etc/hosts` and `/etc/resolv.conf`: the name
servers to ask, the **search** domains to try appending to a short name,
and **options** such as `ndots:N` ("a name with at least N dots is tried
as it is first"). The daemon writes both files for every container at
each start, into the container's directory, and bind-mounts them over the
image's (`run_plan` in `lifecycle.rs`; [chapter 14](14-veth-bridges-netlink.md) §9 lists them by mode).
On the default network:

```text
$ rustlet run --rm alpine sh -c 'cat /etc/resolv.conf; nslookup db 2>&1 | tail -3'
# Generated by rustletd: this container's resolver.
nameserver 192.168.50.1
search lastgateway.lan

** server can't find db.lastgateway.lan: NXDOMAIN
```

The container asks the LAN's router directly, from its own namespace,
through NAT. That address isn't what the host's own `/etc/resolv.conf`
says: on this host that file names only systemd-resolved's stub,
`nameserver 127.0.0.53`, a loopback address that inside a container's
namespace would be the container's own loopback, where nothing listens.
So [`ResolvConf::host`](../../crates/rustlet-net/src/files.rs) notices a file that names only
loopback servers and reads systemd-resolved's list of the servers its stub
forwards to, `/run/systemd/resolve/resolv.conf`, instead, as Docker does;
and if nothing usable is left, the fallback is Google's 8.8.8.8 and
8.8.4.4 (Docker's too). `--dns`, `--dns-search` and `--dns-option` replace
the host's servers, search domains and options. In `--network host` mode
the container shares the host's loopback, so it gets the host's file as it
is, stub and all.

`db` didn't resolve, and couldn't: the default network has no names, as in
Docker. Its containers would have to find each other by address, and
addresses change. Names come with networks you create.

## 2. A network with names

```text
$ rustlet network create backend; rustlet network ls
48834a22af523d5b3c0af0a3ee41e51ce65946a6a3e719d03e4fc348ca31208e
NETWORK ID     NAME      DRIVER    SUBNET
48834a22af52   backend   bridge    10.89.1.0/24
cac3b9f59cd5   bridge    bridge    10.89.0.0/24
$ rustlet run -d --name db --network backend --network-alias database alpine sleep 600
5851451a5fb0b00469ce61f9eb6f884106928a63a7748c96a6e72e007279fec3
$ rustlet run --rm --network backend alpine sh -c 'getent hosts db; getent hosts database; getent hosts DB.backend; getent hosts 10.89.1.2; getent hosts deb.debian.org'
10.89.1.2         db  db
10.89.1.2         database  database
10.89.1.2         DB.backend  DB.backend
10.89.1.2         db.backend  db.backend
2a04:4e42:b::644  debian.map.fastlydns.net  debian.map.fastlydns.net deb.debian.org
```

The container's name, its alias, its name qualified by the network's
(any case), a reverse lookup of its address, and a name from the outside
world: all answered. The outside name came back with an IPv6 address
first, which the upstream had as well as IPv4 ones; a program that
connects falls back to IPv4, since the container has no IPv6 route.

The container's resolver configuration on this network:

```text
# Generated by rustletd: this container's resolver.
nameserver 127.0.0.11
search lastgateway.lan
options ndots:0
```

`127.0.0.11` is the embedded DNS server (§3). `ndots:0` says that every
name, even one without a dot, is first tried as it is: `db` is asked as
`db`, and answered at once. The search domain is kept for names that
aren't found that way (with glibc; musl skips the search list entirely when
a name has at least `ndots` dots, which with `ndots:0` is always).

The same container, asked with busybox's `nslookup`, tells a different
story:

```text
$ rustlet run --rm --network backend alpine sh -c '… nslookup db; nslookup database; nslookup db.backend; nslookup deb.debian.org'
…
Server:		127.0.0.11
Address:	127.0.0.11:53

** server can't find db.lastgateway.lan: NXDOMAIN
…
** server can't find database.lastgateway.lan: NXDOMAIN
…
Name:	db.backend
Address: 10.89.1.2
…
Non-authoritative answer:
deb.debian.org	canonical name = debian.map.fastlydns.net
Name:	debian.map.fastlydns.net
Address: 151.101.46.132
```

busybox's `nslookup` has a resolver of its own, and for a name without a
dot it asks only the name with each search domain appended, whatever
`ndots` says: it asked for `db.lastgateway.lan`, which the server
(rightly) forwarded upstream and the router (rightly) didn't know.
`nslookup db.` (a trailing dot: "this name, as it is") works:

```text
$ rustlet run --rm --network backend alpine nslookup -type=a db.
Server:		127.0.0.11
Address:	127.0.0.11:53

Name:	db
Address: 10.89.1.2
```

Programs use the C library, not busybox's `nslookup`, so the tests check
names with `getent`. An early version of the test used `nslookup` against
a fake upstream that answered *every* name, and the forwarded
`db.test.lan` came back with an address and passed for a local answer;
the fake upstream now knows only names under `example.`, and the test
uses `getent`.

## 3. 127.0.0.11: a server in every container's namespace

The server has to be reachable from inside each container's namespace, at
an address that means "the embedded resolver" in all of them. Docker uses
`127.0.0.11`, a loopback address: every namespace has one of its own, it
never leaves the namespace, and no container uses it for anything else.
Rustlets does the same, so the server needs, in each container's
namespace, a socket at `127.0.0.11`.

A socket belongs to the namespace of the thread that created it (chapter
14 §3). [`start_dns`](../../crates/rustletd/src/network.rs) therefore creates them from a thread inside
the container's namespace, and then hands them to the daemon's ordinary
tokio runtime, which serves them like any other sockets:

```rust
netns::run_in_pinned(&pin, || {
    let at = SocketAddr::new(IpAddr::V4(firewall::DNS_ADDR), 0);
    let udp = std::net::UdpSocket::bind(at).context("bind the DNS server's UDP socket")?;
    let tcp = std::net::TcpListener::bind(at).context("bind the DNS server's TCP socket")?;
    let ports = (port_of(udp.local_addr()), port_of(tcp.local_addr()));
    firewall::run_nft(&firewall::dns_redirect(ports.0, ports.1))?;
    Ok((udp, tcp))
})
```

Port 0: the kernel picks the ports. The program in the container asks
port 53, so a table in **its namespace's** netfilter sends port 53 to
those ports. `nft` is spawned from the same thread inside the namespace,
and a child process starts in its parent thread's namespace, so the table
lands there:

```text
$ nsenter -t 133432 -n nft list ruleset; nsenter -t 133432 -n ss -ulnp; nsenter -t 133432 -n ss -tlnp
table ip rustlet_dns {
	chain output {
		type nat hook output priority dstnat; policy accept;
		ip daddr 127.0.0.11 udp dport 53 dnat to 127.0.0.11:55707
		ip daddr 127.0.0.11 tcp dport 53 dnat to 127.0.0.11:39809
	}
}
State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
UNCONN 0      0         127.0.0.11:55707      0.0.0.0:*    users:(("rustletd",pid=132185,fd=21))
State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
LISTEN 0      128       127.0.0.11:39809      0.0.0.0:*    users:(("rustletd",pid=132185,fd=22))
```

Seen from inside `db`'s namespace: the redirect, and two sockets owned by
`rustletd`, a process that doesn't run in this namespace at all. A query
for `127.0.0.11:53` is rewritten in the `output` hook to port 55707; the
answer from 55707 is rewritten back by conntrack, so the program sees it
come from port 53. `net_dns_port_53_is_redirected_to_the_servers_socket`
checks exactly that in a throwaway namespace.

**Why not bind port 53 itself?** It would be simpler, and the architecture
first planned it. But a socket on `127.0.0.11:53` would take port 53 from
the container's own programs: binding `0.0.0.0:53` overlaps every address
of the namespace, `127.0.0.11` included, and fails while another socket
holds that port on any of them. A container running its own DNS server
(dnsmasq, CoreDNS, Pi-hole) on a user-defined network couldn't start.
Docker's resolver binds random ports and redirects for that reason, and
Rustlets does the same (§2.5 records the deviation from the plan).

## 4. What a DNS message looks like

DNS messages are binary: a 12-byte header, then sections of questions,
answers, authority and additional records. Here is `db`'s `A` question as
a program sends it, and the server's answer (bytes printed by a throwaway
test that ran them through `answer_locally`):

```text
query, 20 bytes
  1a 2b               id
  01 00               flags: RD (recursion desired)
  00 01 00 00 00 00 00 00   1 question, 0 answers, 0 authority, 0 additional
  02 64 62 00         the name: a label of 2 bytes, "db", then the root's empty label
  00 01 00 01         type A, class IN

answer, 36 bytes
  1a 2b               the same id
  85 80               flags: QR (a response) | AA (authoritative) | RD | RA (recursion available); NOERROR
  00 01 00 01 00 00 00 00   1 question, 1 answer
  02 64 62 00 00 01 00 01   the question again
  c0 0c               the answer's name: a pointer (top two bits set) to offset 12, the question's name
  00 01 00 01         type A, class IN
  00 00 02 58         TTL 600 s
  00 04 0a 59 01 02   4 bytes of data: 10.89.1.2
```

Names are length-prefixed labels, and a name already in the message can be
replaced by a two-byte pointer to it (`c0 0c`). The `AAAA` question for
the same name gets the same header with no answer: 20 bytes,
`NOERROR`, zero records. Parsing and building these is
[hickory-proto](https://docs.rs/hickory-proto)'s job (its `Message`, `Query`, `Record`);
everything else in [`dns.rs`](../../crates/rustlet-net/src/dns.rs) is ours.

## 5. What the server answers

One [`Zone`](../../crates/rustlet-net/src/dns.rs) holds every network's names; the daemon adds a
container's when its network is set up and removes them when it is
undone. Each container's server sees it through a [`View`](../../crates/rustlet-net/src/dns.rs): its
network's name and the upstream servers to forward to. The names a
container gets ([`dns_names`](../../crates/rustletd/src/network.rs)): its name, its 12-digit short id,
its hostname and its `--network-alias`es, lowercased, each once.
[`answer_locally`](../../crates/rustlet-net/src/dns.rs) is the whole decision as a pure function, and
the server calls it for every message:

- **`A` for a name on the network**, bare (`db`) or qualified by the
  network's name (`db.backend`), any case, with or without a trailing
  dot: every address registered under that name, in random order (several
  containers can share an alias: a round-robin), TTL 600, authoritative.
- **Any other type for such a name** (`AAAA`, `MX`, …): `NOERROR` with no
  records. The container has no IPv6 address, and an empty answer, unlike
  `NXDOMAIN`, tells the client the name exists, so it doesn't go looking
  for it elsewhere.
- **`PTR` for an address on the network** (`2.1.89.10.in-addr.arpa`):
  `db.backend.`, the first name the address was registered under,
  qualified, as Docker's resolver answers.
- **Not a query**: another opcode gets `NOTIMP`; not exactly one question,
  or a body that doesn't parse, `FORMERR`. A **response** gets nothing at
  all. The first version answered responses with `FORMERR`, as its
  contract said; but `FORMERR` is itself a response, and a server that
  answers responses can be made to bounce messages back and forth with any
  other UDP service that answers what it receives, for ever (the "Loop
  DoS" class, CVE-2024-2169). Unbound and miekg/dns (the library Docker's
  resolver uses) drop responses, and so does this one now.
- **Everything else** is forwarded (§6). With no upstream servers, which is
  the case on an internal network, it gets `REFUSED`: an internal network
  has no way out, and DNS shouldn't be one.

A local answer longer than the client takes over UDP (512 bytes, or the
size its EDNS record offers) is cut to the records that fit, with the
`TC` bit set, so the client asks again over TCP, where it gets them all
(with several dozen containers sharing an alias, the answer would
otherwise be too big for some clients). And a datagram that claims to come
from the server's own address is ignored: only a forged one can, and the
server has no business talking to itself.

## 6. Forwarding

A name the network doesn't have is passed on to the upstream servers
(`--dns`, else the host's, as in §1), one after another until one answers
([`Shared::forward`](../../crates/rustlet-net/src/dns.rs)):

- **The query's own bytes**, with a **fresh random ID** in place of the
  client's, restored in the answer. The server never re-encodes a
  forwarded message, so nothing the client asked (EDNS options, flags,
  case) or the upstream answered is lost or changed.
- **A socket of its own per forward**: for UDP, bound to a port the kernel
  picks and *connected* to the upstream, so the kernel delivers only that
  address's datagrams, and only an answer with the forward's ID is
  accepted. A forger off the path has to guess a 16-bit ID and a port at
  once. The answer is relayed as it is, truncated or not: a truncated
  upstream answer reaches the client with `TC` set, and the client's retry
  over TCP is forwarded over TCP.
- **From the host's namespace.** The forwarding sockets are created by the
  daemon's tokio tasks, which run in the daemon's namespace, so upstream
  traffic goes out like the host's own. (Docker's resolver forwards from
  the container's namespace instead.)
- **Bounded**: `FORWARD_TIMEOUT` (2 s) per upstream, then the next; when
  none answers, `SERVFAIL`. At most `MAX_FORWARDS` (100) forwards in flight
  per server, UDP and TCP together; a query beyond that gets `SERVFAIL` at
  once rather than a task of its own. TCP connections are at most
  `MAX_TCP_CONNECTIONS` (64) per server, each closed after `TCP_IDLE`
  (10 s) without a message.

The unit tests run the server end to end on `127.0.0.1` against fake
upstreams of their own: the ID restored, only the matching answer relayed,
a truncated answer relayed with `TC` and the whole answer over TCP, a
silent first upstream passed over for a second one, all silent giving
`SERVFAIL`, the forward limit, an idle TCP connection closed, and a dropped
server answering nothing more. The daemon test runs a fake upstream on the
test's LAN machine (192.0.2.1), which knows only names under `example.`;
`external.example` resolves through it, `nowhere.invalid` doesn't.

## 7. The server's life

A container's `DnsServer` is two tokio tasks, one per socket, each owning
the tasks of its forwards or connections. It is started with the
container's network ([chapter 14](14-veth-bridges-netlink.md) §8), after its names are in the zone,
and before the container's program runs. When the network is undone,
`DnsServer::close` aborts the tasks and waits for them to go, and with them
the sockets (they hold the container's namespace open, too).

When the daemon restarts, the sockets die with it, while the container
keeps running, and with it the redirect table pointing at ports nobody
holds any more: until a new daemon is up, queries get a "port unreachable"
and the resolver gives up quickly. The new daemon restores the names from
the database, and as it takes the container over ([`resume_network`](../../crates/rustletd/src/network.rs))
binds two new sockets inside the namespace and replaces the redirect
table with one naming their ports. `scripts/smoke.sh` checks that names
still resolve after `systemctl restart rustletd`.

## 8. `/etc/hosts` and `--add-host`

The generated `hosts` ([`files::hosts`](../../crates/rustlet-net/src/files.rs)) starts with Docker's
localhost lines, then the `--add-host NAME:IP` entries, then the
container's own address and hostname:

```text
127.0.0.1	localhost
::1	localhost ip6-localhost ip6-loopback
fe00::0	ip6-localnet
ff00::0	ip6-mcastprefix
ff02::1	ip6-allnodes
ff02::2	ip6-allrouters
10.89.0.2	1c250f9bdbc9
```

`--add-host host.internal:host-gateway` maps a name to the container's
gateway, the host's address on the container's bridge: the way to reach a
service on the host from a container. A container in the host's
namespace gets the host's own `hosts` file plus its `--add-host` entries;
one sharing another container's namespace (`--network container:web`)
gets that container's files. Under `--userns=remap` the files belong to the
container's root, as in Docker, so it may edit them; the next start
rewrites them.

## 9. Differences from Docker and Podman

- Docker's embedded resolver (in libnetwork) also listens at `127.0.0.11` on
  random ports with an iptables redirect in the container's namespace, and
  only on user-defined networks. It forwards from the container's
  namespace; Rustlets forwards from the host's.
- Podman's `aardvark-dns` takes the other road: one server per network,
  in the *host's* namespace, on the network's gateway address
  (`10.88.0.1:53`), named in the containers' `resolv.conf`. Nothing is
  created inside the containers' namespaces, at the price of a host port
  per network, firewall rules to let the queries in, and a check that a
  query comes from the network it was sent to.
- Docker answers `AAAA` for containers with IPv6 addresses; Rustlets'
  networks are IPv4 only.
- Neither Docker's local answers nor Rustlets' carry an EDNS record, which
  RFC 6891 asks a server that understands EDNS to echo; forwarded answers
  keep whatever the upstream put in them.

## 10. Try it

```sh
R="sudo target/debug/rustlet"
$R network create backend
$R run -d --name db --network backend --network-alias database alpine sleep 600
$R run --rm --network backend alpine sh -c 'cat /etc/resolv.conf; getent hosts db database db.backend'
$R run --rm --network backend alpine nslookup db        # busybox: only db.<search domain>
$R run --rm --network backend alpine nslookup db.       # the name as it is
$R run --rm alpine getent hosts db                       # the default network has no names
PID=$($R inspect db | sed -n 's/.*"pid": \([0-9]*\).*/\1/p' | head -1)
sudo nsenter -t $PID -n nft list table ip rustlet_dns
sudo nsenter -t $PID -n ss -ulnp                         # rustletd's socket, in db's namespace
sudo systemctl restart rustletd
sudo nsenter -t $PID -n nft list table ip rustlet_dns   # new ports
$R rm -f db && $R network rm backend
cargo xtask itest -- dn_user dn_internal net_dns         # the tests behind this chapter
```

## Check yourself

1. Why doesn't a container on the default network get `nameserver
   127.0.0.53`, the host's own setting? What does it get instead, and
   from where?
2. What does `ndots:0` change, and why does busybox's `nslookup db` still
   fail where `getent hosts db` succeeds?
3. The DNS server's sockets are served by the daemon's tokio runtime. Why
   do they still listen inside the container's namespace?
4. Why are the server's sockets on random ports with a redirect, rather
   than on port 53? What would break otherwise?
5. Why is the redirect table created by `nft` run from a thread inside the
   container's namespace, and not by the daemon's usual firewall code?
6. In the answer of §4, what do the bytes `c0 0c` mean? Why is the answer
   authoritative?
7. Why does an `AAAA` question for `db` get `NOERROR` with no records
   rather than `NXDOMAIN`?
8. Why must a DNS server never answer a response, not even with an error?
9. Why does the server forward a query's bytes rather than re-encoding the
   parsed message, and why with a new ID over a connected socket of its
   own?
10. The daemon restarts while `db` runs. What happens to a query `db`
    makes in between, and what does the new daemon do to make names work
    again?

## Experiments

- **Watch the conversation.** Inside a container's namespace (`sudo
  nsenter -t <pid> -n tcpdump -ni lo port 53 or host 127.0.0.11`, if
  tcpdump is installed), run `getent hosts db` and `getent hosts
  example.org` in the container. Which ports do you see before and after
  the redirect?
- **A DNS server in a container.** On a user-defined network, run a
  container that binds `0.0.0.0:53` (`nc -lu -p 53` will do). It starts.
  What would have happened if the embedded server held port 53?
- **Round-robin.** Start three containers with the same `--network-alias
  web` and run `getent hosts web` a few times, then `nslookup -type=a
  web.` Which addresses come back, and in which order?
- **No way out.** `rustlet network create --internal inner`, then
  `getent hosts example.org` and `getent hosts <a container on inner>`
  from a container on it. What does the server answer for each, and why?
